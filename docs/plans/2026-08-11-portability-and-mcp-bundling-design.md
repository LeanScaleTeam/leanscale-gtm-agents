# Design — portability outside Claude Code, and MCP bundling

Date: 2026-08-11
Covers: `LeanScaleTeam/marketplace-mcp` issues #1 and #2.
Status: **implemented.** Two things surfaced during the build that this design did not
anticipate — both are recorded under "Discovered during implementation" at the end.

## Why

Two goals that touch the same twenty files, so they are sequenced rather than parallel:

1. Make `skills/` the portable artifact so the agents run on Cursor, VS Code/Copilot,
   Codex CLI and Gemini CLI — not only Claude Code.
2. Bundle the LeanScale MCP into a shortlist of plugins so the corpus wires up on install
   instead of being a separate manual step.

## Corrections to the issues as filed

Both issues say "nine plugins." There are ten — `executive-reporting` was added last and
the count was never propagated. Fixed separately and already landed, along with two gaps
the wrong count was hiding: `executive-reporting` was missing from the README plugin table
and absent from `core/SPEC.md` entirely.

Issue #1 ranks `${CLAUDE_PLUGIN_ROOT}` as the real blocker and `allowed-tools` as
low-priority. That ranking is inverted. `allowed-tools` is advisory and harmless, but
`ToolSearch` appears roughly 100 times **inside the skill bodies** as the tool-discovery
mechanism — every skill opens by resolving its CRM tools through it. Outside Claude Code
the scripts would run correctly against no data. The ToolSearch rewrite is the larger of
the two changes.

Issue #1 also undercounts `${CLAUDE_PLUGIN_ROOT}`: not "two per run skill" but 26
invocation sites across ten run skills, plus 2–10 per setup skill, plus SETUP.md and
README copies — 119 occurrences total. One is a different kind of problem:
`plugins/meeting-to-crm/scripts/report.py:221` *emits* the unexpanded variable into the
rendered HTML, inside the approval command the user is told to paste. That is a live
defect in Claude Code today, independent of portability.

## Decision 1 — root resolution via a generated shim

`setup` resolves the plugin root once, verifies it, and writes a small POSIX shim to
`~/.leanscale-gtm/bin/<plugin>`. Run skills invoke the shim and carry no preamble.

Resolution order inside setup:

1. `$CLAUDE_PLUGIN_ROOT` when set — Claude Code behaviour unchanged.
2. Otherwise the model supplies the directory it loaded the skill from.
3. **Verify** `$AGENT_ROOT/scripts/analyze.py` exists before persisting. This is what makes
   step 2 safe: a wrong path fails loudly once, at setup, rather than silently on each run.
4. Persist `agent_root` into `~/.leanscale-gtm/<plugin>.json` and write the shim.

The shim itself re-prefers `$CLAUDE_PLUGIN_ROOT` at call time and falls back to the baked
path, so a marketplace update that relocates the plugin cache cannot leave a Claude Code
user with a stale shim. Resolution lives in exactly one place.

```sh
#!/bin/sh
# LeanScale GTM Agents — generated by /<plugin>:setup. Re-run setup to regenerate.
BAKED='<resolved at setup time>'
[ -n "$1" ] || { echo "usage: <plugin> <script> [args]" >&2; exit 2; }
script="$1"; shift
for root in "$CLAUDE_PLUGIN_ROOT" "$BAKED"; do
    [ -n "$root" ] && [ -f "$root/scripts/$script.py" ] && exec python3 "$root/scripts/$script.py" "$@"
done
echo "<plugin>: cannot locate scripts/$script.py — re-run /<plugin>:setup" >&2
exit 2
```

Call sites become one line, with the subcommand naming the script:

```bash
"$HOME/.leanscale-gtm/bin/crm-hygiene" analyze --raw "$RUN/raw" --out "$RUN"
"$HOME/.leanscale-gtm/bin/meeting-to-crm" diff approve --run "$RUN" --token "$TOK" --apply
```

Shim generation lives in `core/lib/config.py` behind a `__main__` block so it vendors to
all ten plugins with no new files:

```bash
python3 "$AGENT_ROOT/scripts/lib/config.py" install-shim --plugin crm-hygiene --root "$AGENT_ROOT"
```

Rejected: a seven-line inline preamble repeated at 26 sites (copy-paste surface); a
`leanscale-gtm` CLI on PATH (contradicts INSTALL.md's "nothing to `pip install`").

## Decision 2 — capability-first tool resolution

Each skill's §1 states the capability contract and lists concrete tool names as the
fallback. ToolSearch is demoted from the contract to "the fastest route when available."

```
Required capabilities: `crm.query`, `crm.describe`.

Find the connected tools that provide them. If ToolSearch is available, that is the
fastest route. Otherwise match against your connected tools — commonly named:

  crm.query     salesforce: run_soql_query
                hubspot:    hubspot-search-objects / hubspot-list-objects
  crm.describe  salesforce: run_soql_query (+ useToolingApi)
                hubspot:    hubspot-list-properties

Report which tool resolved for each capability before proceeding.
```

Capabilities across the suite: `crm.query`, `crm.describe`, `crm.write`, `transcripts.*`,
`comms.search`, `docs.read`. Each skill inlines only what it needs. The canonical map is
added to `core/SPEC.md` as the authoring reference and inlined per skill so a running agent
never follows a pointer mid-run.

`allowed-tools` frontmatter is left alone — advisory, and all three existing variants are
correct for Claude Code.

## Decision 3 — MCP bundling and key acquisition

`.mcp.json` ships in three plugins where the corpus genuinely improves output:
`forecast-agent` (benchmarks), `stage-architect` (stage-design playbook), `crm-hygiene`
(hygiene/migration playbooks). Not all ten.

The key is **optional but prompted**. Agents run without it and note in their output when a
finding could have been enriched but wasn't.

Setup detects a missing or invalid `LEANSCALE_MCP_KEY`, offers to fetch one for a work
email, and states what it will send and where *before* sending. On success it writes
`~/.leanscale-gtm/mcp.json` at mode 0600 and prints the exact `export` line for the user
to paste.

**Setup never edits the user's shell rc.** `.mcp.json` can only interpolate a real
environment variable, so "write it where the shell will pick it up" means appending to
`.zshrc`/`.bashrc`/`config.fish` — a mutation to a file the tool does not own, on a suite
whose own trigger phrases include "we're doing a security review of Salesforce." One paste,
once, is the right trade. Nothing outside `~/.leanscale-gtm/` is ever touched.

### Known and accepted

`claude mcp list` reports the server as connected even with no key, because `GET /mcp`
returns 200 without one. Anyone debugging will be misled. Setup catches it instead; not
worth blocking on.

Issue #2's 401 behaviour was verified by calling the endpoint directly, not by driving a
tool call through an installed plugin. Reproduce in-client before relying on that error
text as the onboarding message.

## Decision 4 — reconcile the trust promise

INSTALL.md currently promises "No telemetry, no phone-home, no uploads. The only network
traffic is the connectors you authorised." An opt-in key fetch contradicts it. The promise
is rewritten to the more precise and still-stronger claim — no CRM data leaves the machine,
ever — with the optional email fetch named explicitly as the one exception.

## Discovered during implementation

**1. `${CLAUDE_PLUGIN_ROOT}` is not only used for scripts.** It also addresses
`config.example.json` and `fixtures/`, which a shim cannot exec. The shim therefore gained a
`--root` query that prints the resolved plugin directory:

```bash
AGENT_ROOT="$("$HOME/.leanscale-gtm/bin/crm-hygiene" --root)"
cp "$AGENT_ROOT/config.example.json" ~/.leanscale-gtm/crm-hygiene.json
```

Resolution still lives in one place; `--root` just exposes it. 23 of the 86 references were
this shape.

**2. Skill names collide outside Claude Code.** Every plugin ships skills literally named
`run` and `setup`. Claude Code namespaces them (`/crm-hygiene:run`), so the collision is
invisible there — but a flat `~/.cursor/skills` directory would receive ten skills called
`run`. `tools/install-skills.py` therefore installs them as `<plugin>-run` / `<plugin>-setup`
and rewrites the frontmatter `name:` to match, since a skill whose directory and `name:`
disagree is ignored by some hosts. Issue #1's "copy `skills/` into the target directory"
would have shipped broken.

The same script also writes the shim pointing back at the clone, because after copying, the
skill's own advice ("two levels up from `skills/setup/`") resolves to the target directory,
which contains only markdown — no `scripts/`.

### Verified

- Full `crm-hygiene` pipeline end to end with `CLAUDE_PLUGIN_ROOT` unset: 42 findings,
  Hygiene Index 67/100, all four artifacts written.
- The `sales-coach` SETUP.md demo block run verbatim under a fake `HOME`, with no
  `CLAUDE_PLUGIN_ROOT` and a redirected `LEANSCALE_GTM_HOME` — the case where the shim must
  be found in the real home while config is read from elsewhere.
- 18 new `core/selftest.py` checks covering shim generation, precedence, spaces in paths,
  stale-path fallback, and key file permissions.
- `tools/qa.py` gates the invariants; confirmed it fails when a `${CLAUDE_PLUGIN_ROOT}` is
  reintroduced into a run skill.

## Out of scope

Rewriting the skills (they are already the right artifact). Dropping the plugin (still the
best Claude Code experience). Making the agents work in ChatGPT web or Claude.ai — both
need local script execution against the customer's CRM, and never will. The client matrix
in INSTALL.md should say so plainly.
